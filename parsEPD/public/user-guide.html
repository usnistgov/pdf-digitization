Overview

parsEPD is a NIST tool that converts Environmental Product Declarations (EPDs) from PDF or HTML format into a standardized, machine-readable JSON format called openEPD. The conversion is powered by a large language model (LLM) that reads the document, validates it as a genuine EPD, and extracts structured data conforming to the openEPD schema.

EPDs are formal documents that declare the environmental impact of construction products. They are essential for calculating embodied carbon in buildings, but are typically published as PDFs that resist automated processing. parsEPD eliminates the manual extraction step.

parsEPD is designed for EPDs that comply with ISO 14025 and EN 15804. Documents that contain environmental data but are not formal EPDs (LCA reports, sustainability brochures) will be rejected by the validation step.

Supported File Types

Format Extensions Notes
PDF .pdf Text is extracted using pdfjs. Scanned/image-only PDFs are not supported — the text must be selectable.
HTML .htm, .html Full HTML files only. Single-page EPD web exports work well.
  • Maximum file size: 5 MB
  • Only one file at a time — uploading a new file replaces the previous one
  • Only the most recent upload is available for conversion
Scanned PDFs (images of text) cannot be processed. The PDF must contain selectable text. If you can highlight text in a PDF viewer, parsEPD can read it.

Model Selection

parsEPD routes LLM requests through an internal NIST proxy. Select a model from the dropdown in the sidebar before uploading your file. The model choice affects output quality, speed, and handling of complex multi-product EPDs.

Llama 4 Maverick 17B DefaultRecommended

A strong general-purpose model. Good balance of speed and accuracy for most standard EPDs. Use this as the starting point.

GPT OSS 120B

Larger model with higher capacity. Better for complex EPDs with many products, dense tables, or unusual formatting. Slower than Maverick.

Nemotron Super 120B

NVIDIA's large open-source model. An alternative to GPT OSS for difficult documents. Try this if GPT OSS produces incomplete or malformed output.

If extraction fails or produces clearly wrong values, try a larger model (GPT OSS or Nemotron) before concluding the EPD is unsupported.

How It Works

After uploading, parsEPD runs a sequential 7-step pipeline. Status is shown in the sidebar.

  1. Text Extraction
    For PDFs, pdfjs reads each page and concatenates all text. For HTML files, the markup is converted to plain text. The extracted content is then passed to subsequent steps.
  2. Security Sanitization
    The extracted text is scanned for prompt injection patterns — instructions embedded in the document that could manipulate the LLM. Detected lines are redacted before any LLM call is made.
  3. EPD Validation
    The LLM checks whether the document is a genuine EPD per the definition in ISO 14025 and EN 15804. It must have: a program operator, verification statement, declared unit, LCIA indicators, and a validity period. Documents that fail this check are rejected with a "Not an EPD" message and processing stops.
  4. Product Category Identification
    The LLM classifies the EPD into a product category (e.g., Ready Mix Concrete, Asphalt, Cement, Gypsum). The category determines which category-specific schema extensions are included in the output JSON.
  5. Product Count Detection
    The LLM determines how many products are declared in the EPD. Some EPDs cover multiple products (e.g., a concrete EPD declaring multiple mix designs). Multi-product EPDs produce an array of JSON objects.
  6. JSON Extraction
    The LLM extracts all structured data from the EPD and generates a complete openEPD JSON object. This is the most LLM-intensive step and may take 30–90 seconds depending on document length and model selection.
  7. Schema Validation
    The extracted JSON is validated against the openEPD JSON schema using AJV. Validation results (pass or list of errors) are shown below the JSON viewer. Schema errors do not prevent download — they indicate fields that may need manual correction.

Output Format

parsEPD outputs JSON conforming to the openEPD standard — an open schema for machine-readable EPD data maintained by Building Transparency. This format is accepted by tools like EC3 (Embodied Carbon in Construction Calculator).

Top-Level Fields

Field Description
doctype Always "OpenEPD"
product_name Name of the declared product
manufacturer Company that produced the product, including location
plants Manufacturing plant(s) where the product was made
declared_unit Quantity and unit the environmental impacts are declared per (e.g., 1 m³)
pcr Product Category Rule the EPD was developed under
program_operator Organization that administers the EPD program
date_of_issue / valid_until EPD validity period

Environmental Impacts (impacts.TRACI 2.1)

Impacts are reported by life cycle stage (A1, A2, A3, A1A2A3) where available:

Key Impact Category
gwp Global Warming Potential (kg CO₂ eq)
odp Ozone Depletion Potential (kg CFC-11 eq)
ap Acidification Potential (kg SO₂ eq)
ep Eutrophication Potential (kg N eq)
pocp Photochemical Ozone Creation Potential
gwp_biogenic Biogenic GWP
gwp_luluc Land use and land use change GWP

Category-Specific Extensions (specs)

For recognized product categories, additional fields are extracted:

  • Asphalt — binder grade, mix type (WMA/HMA), RAP/RAS content, aggregate size, temperature
  • Cement — cementitious composition (OPC, fly ash, GGBS, silica fume, etc.), ASTM/EN type
  • Ready Mix Concrete — strength, slump, w/c ratio, exposure classes, cementitious composition, application type

Using the Results

Viewing the JSON

The extracted JSON is displayed in an interactive editor on the right side of the screen. You can expand and collapse nested objects, and edit individual values directly in the viewer.

Downloading

Click the Download button below the JSON viewer to save the file as .json. The filename defaults to the product name extracted from the EPD.

Starting Over

Click Start Over in the sidebar to clear all state and upload a new EPD. This action cannot be undone — a confirmation dialog will appear before clearing.

The JSON editor allows manual corrections. If the LLM extracted a wrong value, you can fix it before downloading. Schema validation errors shown below the viewer identify specific fields that need attention.

Troubleshooting

"Not an EPD" error

The validation step determined the document does not meet EPD requirements. Possible causes:

  • The document is an LCA report, sustainability assessment, or product brochure — not a formal EPD
  • The EPD is a scanned image and text extraction returned garbled content
  • The document is partially loaded (try a fresh download of the PDF)

Incomplete or missing fields in output

If some fields are null or "--":

  • The EPD may genuinely not report those values (common for older EPDs)
  • The data may be in a table format the model missed — try a larger model (GPT OSS or Nemotron)
  • Very long EPDs may exceed the model's context window — consider a model with higher capacity

Schema validation errors

Validation errors appear below the JSON viewer after extraction. Common issues:

  • Wrong data type for a field (e.g., a string where a number is expected) — correct in the JSON editor
  • Missing required fields — check if the EPD actually contains the data and add it manually if so
  • Units formatted differently than schema expects — normalize to the schema's expected unit string

Slow extraction or timeout

  • Large PDFs (50+ pages) take longer — expect 60–120 seconds for complex documents
  • If the page seems unresponsive, wait up to 3 minutes before refreshing
  • Multi-product EPDs are more demanding — use GPT OSS or Nemotron for documents with 3+ products

Uploaded file not accepted

  • File must be .pdf, .htm, or .html
  • File size limit is 5 MB
  • Only one file at a time is supported

About

parsEPD is developed by the National Institute of Standards and Technology (NIST) as part of the Building System Economics project. The goal is to make EPD data machine-accessible at scale, enabling automated embodied carbon calculations for buildings.

The openEPD schema is maintained by Building Transparency. parsEPD is open source — source code is available on GitHub.
